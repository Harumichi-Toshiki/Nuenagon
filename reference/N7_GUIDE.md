# Nuenagon：Shikibu M7 の評価関数への対応 指南書

対象：Nuenagon の実装担当（N5.5・N6 の後に入る段階。仮に **N7** と呼ぶ）
目的：Shikibu M7（評価関数の構造の実験室、設計書 v1.8 §S12）で学習した評価関数を、Nuenagon で動かして**対局で比べられる**ようにする。重い評価関数でも強く使えるように、速さの仕組みもここで入れる。

---

## 1. 背景

- Shikibu M7 では、評価関数の構造を `<特徴>_<W>x2-<L1>-<L2>[_f][_psqt][_k3k3]` の名前1つで切り替えて学習し、val_loss で比べられる。
- 比べた結果の良いものを、最後は**ノード数固定の対局**（探索の差を除いた評価関数の差）と**持ち時間の対局**（重さ込みの強さ）で確かめる。そのために、Nuenagon が全部の構造を読めることが必要。
- 今の Nuenagon（N5H）は、RayPair_v0（W128-16-16）と、やねうら王の `halfkp_256x2-32-32` だけを読める。

## 2. 対応する構造（優先度順）

| 優先 | 構造 | ファイル | 備考 |
|---|---|---|---|
| A | halfkp を**任意の幅**で | nn.bin | N5H の HalfKP を、幅を実行時に決める形にする |
| A | halfka1・halfka2・halfkahm1・halfkahm2 を任意の幅で | nn.bin | 玉も特徴に入る。hm は左右反転あり |
| B | raypair0・raypair1 を任意の幅で | .shk | ヘッダの W・L1・L2 に従う（§F3.1 は「未対応なら拒否してよい」なので、対応を広げるだけ） |
| C | raypair0k・raypair1k、psqt、k3k3 | 未定 | Shikibu 側もまだ書き出せない。ファイル形式は、A・B の後で設計担当が決める（§7） |

幅の範囲：W は 32 の倍数（32〜8192）、L1・L2 は 8 の倍数（8〜1024）。Shikibu はこの範囲しか出さない。

## 3. 定義（正解は Shikibu のリポジトリのテスト）

**特徴・推論・ファイルの並びの正解は、Shikibu の `tests/nnue_ref.py`・`tests/nnue_nnbin.py`・`tests/golden/nnue_golden.json`**。次の N7 のキットで Nuenagon の `tests/` にも同じものを入れる。やねうら王（コミット 32165a8）を 12 通りの構造でビルドし、乱数の重みで静的評価値が全局面一致することを確かめてある。**やねうら王のソースは読まない・写さない（GPL）**。

要点（詳しくは `nnue_ref.py` の冒頭）：

### 3.1 駒の番号（BonaPiece）と特徴
- マス：`sq = 筋の番号 × 9 + 段の番号`（1一 = 0、9九 = 80）。後手の視点は `80 − sq`。
- 持ち駒 0〜89、盤上 90〜1547（N5H の HalfKP と同じ）。HalfKA の系統だけ、玉 `f_king = 1548 + sq`・`e_king = 1629 + sq` を足す。
- 駒箱の駒は駒の番号 0 として数える（HalfKP は 38 個、HalfKA は 40 個になるまで）。

| 特徴 | 特徴の番号 | 次元 |
|---|---|---|
| halfkp | K × 1548 + 駒（玉以外） | 125,388 |
| halfka1 | K × 1710 + 駒（両玉を含む） | 138,510 |
| halfka2 | K × 1629 + 駒'（e_king を f_king と同じ番号にする） | 131,949 |
| halfkahm1 | halfka1 の左右反転つき | 76,950 |
| halfkahm2 | halfka2 の左右反転つき | 73,305 |

- **左右反転（hm）**：自玉 K の筋が 6〜9 筋（筋の番号 5〜8）なら、K を `Mir(K) = (8 − 筋) × 9 + 段` にし、盤上の駒（玉を含む、番号 ≧ 90）のマスも Mir にする。持ち駒は変えない。K は 0〜44 になる。

### 3.2 推論（N5H と同じ。幅が変わるだけ）
```
acc[p]  = bias(int16, W) + Σ 重みの行(int16, W)        # int16 の範囲で
x       = [clamp(acc[手番], 0, 127), clamp(acc[相手], 0, 127)]   # 2W 個の uint8
h1      = clamp((b1 + w1·x) >> 6, 0, 127)              # L1
h2      = clamp((b2 + w2·h1) >> 6, 0, 127)             # L2
raw     = bo + wo·h2
cp      = raw / FV_SCALE（0 方向への切り捨て）
```

### 3.3 ファイルの並び
- ヘッダ：版 0x7AF32F16、ファイルのハッシュ、構造の文字列（中身は確かめなくてよい）。
- 特徴変換：ハッシュ（= 特徴のハッシュ ^ 2W）、bias int16[W]、重み int16[次元][W]。
- ネットワーク：ハッシュ、層ごとに bias int32[出力] と重み int8[出力][**pad32(入力)**]。
  **入力の幅は 32 の倍数に切り上げ**（例：L1 = 8 なら第2層の重みは 1 行 32 バイト、後ろ 24 バイトは 0）。
- 特徴のハッシュ：halfkp 0x5D69D5B8、halfka1 0x5F134CB8、halfka2 0x5F234CB8、halfkahm1 0x7F134CB8、halfkahm2 0x7F234CB8。
- ネットワークのハッシュは `nnue_nnbin.py` の `hashes()` の式。
- **構造をファイルから決める方法**：ファイルの大きさとハッシュから、特徴の種類・W・L1・L2 を決められる。いちばん簡単なのは、構造の文字列の `Features=…[N->Wx2]` と `AffineTransform[L2<-L1]` を読んで候補を出し、**ハッシュとファイルの長さが合うことで確かめる**こと。合わなければ読み込みを拒否する。

## 4. 実装の指針

### 4.1 幅を実行時に決める
- テンプレートで幅を固定すると、構造ごとに exe が要る。実験の段階では**実行時の幅**（W・L1・L2 を変数で持つ）にする。
- AVX2 の内側のループは「32 の倍数」「8 の倍数」を前提に書ける（Shikibu の制約がそうなっている）。
- 大会で使う構造が決まったら、その幅だけテンプレートで特殊化した速い経路を足せばよい（後回し）。

### 4.2 差分更新
- HalfKP：今の N5H と同じ。自玉が動いたら、その視点だけ作り直す。
- HalfKA：**相手の玉が動いたときも差分**（相手の玉は普通の駒と同じ扱い。自分の視点の特徴が1つ消えて1つ増える）。自玉が動いたら、その視点だけ作り直す。
- hm：自玉が 5 筋 ↔ 6 筋をまたいで反転の向きが変わったときも作り直し（自玉が動いたときは常に作り直すので、自然に含まれる）。

### 4.3 重い評価関数を速くする（やねうら王・Stockfish で一般的な方法）
1. **Finny テーブル（accumulator の cache）**：玉の位置（K）ごとに「最後に作った蓄積値と、そのときの駒の集合」を視点ごとに覚えておく。自玉が動いて作り直すときは、その K の記録との差分だけ足し引きする。自玉の移動が多い終盤や W が大きいときに大きく効く。
2. **差分の遅延更新**：do_move のときは変わった特徴だけを記録し、評価するときに、作り直し済みの祖先からまとめて足し引きする（枝刈りで評価されない局面の更新を省く）。
3. **L1 の疎な入力**：x（uint8、2W 個）の大半は 0。0 でない要素の番号を集めて（AVX2 で 4 バイトずつ）、その列だけ積和する。W が 512 以上なら必須。
4. 第2層以降は小さいので、普通の AVX2 の積和でよい（`maddubs` + `madd`）。

目安：やねうら王の halfkp_256 で 1スレッド 170万 NPS（持ち主の PC）。Nuenagon は同じ評価関数で 100万 NPS を切っていた（N5H）。**評価関数の重さで負けないこと**が、構造の比較の前提。

### 4.4 RayPair の任意の幅（.shk）
- ヘッダの W・L1・L2 に従う。量子化は §E4 のまま（ft ×127、隠れ層 ×64、bias ×8128）。
- RayPair の差分更新は今のまま。幅が変わるだけ。

## 5. USI・DJP 側
- `EvalFile` の判定は今と同じ（先頭4バイトが 0x7AF32F16 なら nn.bin、それ以外は .shk）。
- 読み込んだら `info string` に構造を1行出す（例：`info string eval halfkahm2_512x2-16-32 FV_SCALE=13`）。対局の記録で取り違えないため。
- `FV_SCALE` は今のオプションのまま。Shikibu の書き出しが表示する値を使う。
- DJP の `wr` の eval_scale は、nn.bin のとき既定 600（N6 のとおり）。Shikibu の checkpoint の eval_scale と合わせたいときは `dajo set eval_scale=…`。

## 6. 確かめ方（次のキットのテストの予定）
1. `nnue_golden.json` の全構造（12 通り・16 ファイル）で、Nuenagon の `eval` 命令の値が正解と1点も違わないこと。nn.bin は `nnue_nnbin.make(path, arch, seed, scale)` で作り直せる（SHA-256 で確認）。
2. 差分更新と全計算が一致すること（ランダムに指し進めて、毎手の蓄積値を比べる。HalfKA の玉の移動・hm の反転・駒箱を含む局面）。
3. 速さ：halfkp_256x2-32-32 で N5H 比、halfkahm2_512x2-16-32・halfkahm2_1024x2-8-32 での NPS を報告。
4. 決定的モードでノード数が SIMD の有無で同じ（N5 と同じ決まり）。
5. RayPair・N5H の HalfKP での探索の結果は変えない（RayPair の既定の .shk で、N5.5 の決定的モードのノード数が変わらないこと）。

## 7. 優先度 C（独自の構造）について
- raypair0k・raypair1k（RayPair ＋ 玉の周り 5×5、Shikibu の `tests/kingzone_ref.py`）、psqt（特徴ごとの点数を直接足す）、k3k3（両玉の段で層を 9 組から選ぶ）。
- Shikibu 側も、まだ書き出し形式が無い。val_loss の比較で効き目がはっきりしたものだけ、設計担当が .shk の拡張（v2）を決めて、Shikibu と Nuenagon に同時にキットを出す。
- それまで Nuenagon 側で準備しておけるのは、「層が S 組ある」「出力に線形の項を足す」形を入れやすい推論の作り（4.1 の実行時の幅の延長）だけでよい。

## 8. 進め方の提案
- N5.5（探索の改良）→ N6（DJP）→ **N7（この指南書：A・B と速さ）**の順。
- 大会（電竜戦本戦）に間に合わせる必要があるのは、**実際に使う1つの構造**だけ。M7 の比較で候補が決まったら、その構造を A の中で最優先にする。
